# GraphMem 高预算下的 LLM 增强方向

## 1. 背景与目标

当前实验结果显示：

- `all-hit` 与 `recall` 已在高位（约 95%+），继续提升总体召回存在天花板效应。
- `llm-edge` 在全量启用下显著增加了 token 消耗，但全局召回未明显改善。
- 从用户体验看，在线阶段（检索+回答）延迟改善具有实际价值。

因此，后续策略建议从“全量加 LLM”转为“按环节、按条件定向加 LLM”，在预算充足（`<200K token/题`）前提下优先优化：

1. 复杂题准确性（特别是 `multi-session` / `temporal-reasoning`）
2. 在线 latency（用户可感知）
3. 结果稳定性（p95 与尾部样本）

---

### LLM 辅助连边
主要问题在于目前的树形结构，是一个session形成一棵树，然后对话细节会被拆分成leaf
连边只连了不同树的root node，所以导致目前的root召回率很高，但是具体到包含答案的leaf召回率低，只有56%，相应的回答准确率不高
目前的优化方案
1. 构建 添加llm优化构建时的连边路径 root-leaf leaf-leaf
2. 检索 如何才能检索到相关leaf


## 2. 可添加 LLM 的候选环节（按优先级）

## 2.1 构建后摘要修复（离线）

**目标**  
修复 `summary_parse_error` / `summary_truncation` 导致的结构退化，减少脏摘要对后续检索的负面影响。

**触发条件（建议）**

- `summary_parse_error_count > 0`
- `summary_truncation_count > 0`
- 或摘要长度/结构异常（字段缺失）

**LLM任务**

- JSON 结构补全（恢复 `m/k` 等关键字段）
- 将截断摘要重写为标准 compact schema

**预期收益**

- 复杂题 recall 稳定性提升
- 降低 build 退化传导到 retrieval/answer 的概率

**成本属性**

- 离线成本，不直接影响用户在线时延

---

## 2.2 检索后轻量重排（在线）

**目标**  
在召回候选已较高的前提下，用小 LLM 提升“证据质量排序”，改善答案上下文质量。

**触发条件（建议）**

- 仅对复杂题型或高不确定问题触发
- 仅重排 top-N 候选（如 8~16），避免全量重排

**LLM任务**

- 基于问题目标判断候选证据“相关性 + 完整性”
- 输出排序分数或保留列表

**预期收益**

- 复杂题准确性提升（尤其聚合类问题）
- 若最终上下文更紧凑，`answer_latency` 可能下降

**成本属性**

- 在线成本，需要严格限制触发范围

---

## 2.3 复杂题子查询分解（在线条件触发）

**目标**  
提升多证据问题（`gold>2`）覆盖率，缓解单 query 对分散证据召回不足的问题。

**触发条件（建议）**

- `question_type` 属于 `multi-session` / `temporal-reasoning`
- 或 query 判定为计数/比较/时间链问题

**LLM任务**

- 将原问题分解为 2~3 个子查询
- 多轮检索后合并候选并去重

**预期收益**

- `all-hit` 与 `recall` 在高复杂子集提升更明显

**成本属性**

- 在线成本中等，建议仅对复杂题启用

---

## 2.4 回答前证据充分性判定（在线）

**目标**  
降低“该拒答却作答”与“证据齐全却拒答”的双向错误。

**触发条件（建议）**

- 回答前统一触发一个轻量判定
- 或仅在低置信检索样本触发

**LLM任务**

- 判断当前证据是否足以支持最终结论
- 不足则触发补检索或拒答模板

**预期收益**

- abstain 相关错误下降
- 答案质量与一致性提升

---

## 3. 建议暂缓的方向

以下方向在当前阶段建议谨慎：

- 全量题、全节点的额外 LLM 连边（成本高，收益易被稀释）
- 不设门控的多轮 LLM 迭代检索（在线延迟风险高）
- 在召回已高位时继续追求全局 recall 微涨（边际收益低）

---

## 4. 推荐实验路线（最小可行）

建议从两条线并行：

1. **离线线：摘要修复**
   - 对 parse/truncation 样本做定向修复
2. **在线线：复杂题分解检索**
   - 仅在 `multi-session` / `temporal` 启用

每条线先做小样本 A/B（例如 50~100 题），通过后再全量。

---

## 5. 验收指标（避免只看全局平均）

建议固定以下指标作为实验门槛：

- 准确性相关
  - `retrieval_all_hit_rate`（全量 + 复杂子集）
  - `avg_recall`（全量 + `gold>2` 子集）
  - abstain 错误计数（`answer_should_abstain` / `answer_over_abstain`）
- 体验相关
  - 在线 latency：`retrieval_latency`、`answer_latency`（建议看 p50/p95）
- 成本相关
  - `avg_tokens_per_question`
  - 每阶段 token 占比（确认新增 token 用在预期环节）

---

## 6. 一句话策略

在高召回基线下，后续不应追求“全量再提 1% recall”，而应采用：

**“按复杂度条件触发的 LLM 增强，把 token 精准投到高难样本与用户可感知体验上。”**
